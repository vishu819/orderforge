01 · The picture to remember

Docker packages an application and runs it as an isolated process. Your Java application is still Java: Docker supplies its runtime environment and manages how it starts, connects, and accesses files.

Source + build configuration→ build →Image→ create/start →Container
ThingPlain meaningOrderForge example
DockerfileInstructions for building an image.Build Java, copy its JAR, choose the runtime user.
ImageA packaged filesystem and startup configuration.Java 21 runtime + Product JAR. No live orders.
ContainerAn instance created from an image, with its own process and writable filesystem layer.The running Product JVM.
Docker EngineThe service that builds images and manages containers.The Docker CLI asks it to start your services.
Docker DesktopDesktop application that manages the local Docker environment.Linux containers on your Mac run through a Linux VM.
RegistryA service for storing and distributing images.Docker Hub supplies the Temurin base images. We have not published OrderForge images yet.
ComposeA file and CLI for running several services together.Our two services, their network, ports, URL, and readiness rule.

Containers share the kernel of their Linux host; they are not a full virtual machine each. They still need a compatible platform: your Mac builds ARM64 images, while a future server might use AMD64. Portability does not remove architecture differences.

Remember: Dockerfile = instructions. Image = package. Container = instance. Registry = distribution.

03 · Understand your Dockerfile

Product’s current Dockerfile is shown below. Order has the same build structure, a different JAR name and port, and does not install curl.

FROM eclipse-temurin:21-jdk AS build

WORKDIR /build

COPY .mvn/ .mvn/
COPY mvnw pom.xml ./
RUN chmod +x mvnw
RUN ./mvnw -B dependency:go-offline

COPY lombok.config ./
COPY src/ src/
RUN ./mvnw -B package -Dmaven.test.skip=true

FROM eclipse-temurin:21-jre

RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

RUN groupadd --gid 10001 appgroup \
    && useradd --uid 10001 --gid appgroup \
       --no-create-home appuser

WORKDIR /app

COPY --from=build \
    /build/target/product-service-0.0.1-SNAPSHOT.jar \
    app.jar

EXPOSE 8081

USER 10001:10001

ENTRYPOINT ["java", "-jar", "app.jar"]
InstructionWhat happens
FROM …21-jdk AS buildStart a build stage with Java compilation tools. Maven Wrapper supplies Maven separately.
WORKDIR /buildSet the working directory for following build commands.
COPY .mvn + mvnw + pom.xmlBring in the wrapper, its configuration, and dependency/build definitions.
RUN chmod +x mvnwAllow the Linux build to execute the wrapper.
RUN … dependency:go-offlinePrepare dependencies and plugins for cache reuse. Later packaging can still need additional downloads.
COPY lombok.config / COPY srcInclude annotation-processing configuration and source. Docker does not see arbitrary laptop files automatically.
RUN … packageCompile and create the executable JAR. Tests are deliberately skipped in our current learning build.
Second FROM …21-jreStart the final runtime stage. It does not inherit all build-stage files.
apt-get … curlInstall the command used by Product’s Compose health check. Remove package-index files afterward.
groupadd / useraddCreate a named group and user with fixed numeric IDs.
COPY --from=buildCopy just the executable JAR from the build stage into /app/app.jar.
EXPOSEDocument the intended application port. Does not publish it or configure Spring Boot.
USER 10001:10001Run subsequent commands and the application with reduced privileges.
ENTRYPOINT ["java", …]Start Java directly rather than through a shell. This helps deliver stop signals to Java.

JDK, JRE, Maven, Tomcat

The JDK includes javac and development tools. The JRE supplies the JVM and runtime libraries. Maven coordinates compilation and packaging; it is not part of the JDK. Tomcat serves HTTP inside your Spring Boot JAR. A separate Tomcat installation is unnecessary for this executable-JAR setup.

The multi-stage build makes the build environment explicit and keeps source/build tools out of the final image. Exact reproducibility also needs controlled dependencies and base-image versions; our moving Temurin tags are not fully pinned.

Reference: Docker: multi-stage builds.

04 · Cache and build context

The build context is the directory Docker receives for a build. In Compose, Product’s context is ./product-service. Its Dockerfile can copy files from that context, except those excluded by .dockerignore.

Our ignore file excludes target/, .git/, .idea/, and *.iml. The JAR is built inside Docker, so local target output is unnecessary. This is separate from Git’s .gitignore.

Copy infrequent changes first

COPY .mvn/ .mvn/
COPY mvnw pom.xml ./
RUN chmod +x mvnw
RUN ./mvnw -B dependency:go-offline
COPY lombok.config ./
COPY src/ src/
RUN ./mvnw -B package -Dmaven.test.skip=true

Changing only source lets Docker reuse the earlier dependency step. Changing pom.xml invalidates that copy and subsequent steps in this stage. On a fresh machine or CI runner there may be no cache; a cache makes builds faster, not correct.

The failure you already diagnosed

Order compiled on the laptop but failed in Docker because lombok.config was not copied. The lesson: inspect the first meaningful Maven error above Docker’s final “exit code 1” summary. Ask whether every build input is present.

05 · Follow one order request

Laptop client
localhost:18082→Order container
8082HTTP →product-service:8081
Product container

The browser or curl reaches Order through a published host port. Order then makes a normal HTTP call on the shared Compose network. Product returns catalog data; Order captures the price, computes totals, and stores the order in its JVM memory.

CallerCorrect destinationReason
Browser on laptophttp://localhost:18081/products/prod-118081 is the published laptop port.
Order containerhttp://product-service:8081/products/prod-1Compose resolves service names; use the container port.
Product health-check processhttp://localhost:8081/actuator/health/readinessThe check runs inside Product’s own container.

18081:8081 means host:container. EXPOSE alone does not provide that mapping. Container-to-container access does not require publishing Product’s port to the laptop.

Compose provides service-name DNS. Use names rather than container IP addresses, which can change. “localhost” always refers to the caller’s own network environment here. It is not a universal name for your Mac.

Our published ports do not specify a host address, so they are not restricted to loopback by this file. For laptop-only access you could use 127.0.0.1:18081:8081. That change is not applied by this guide.

Reference: Docker: Compose networking.

06 · Read your Compose file

This is the actual configuration at the time this guide was created.

services:
  product-service:
    build: ./product-service
    ports:
      - "18081:8081"
    healthcheck:
      test: ["CMD", "curl", "--fail", "--silent", "--max-time", "2", "http://localhost:8081/actuator/health/readiness"]
      interval: 10s
      timeout: 3s
      start_period: 30s
      retries: 3

  order-service:
    build: ./order-service
    ports:
      - "18082:8082"
    environment:
      PRODUCT_SERVICE_BASE_URL: http://product-service:8081
    depends_on:
      product-service:
        condition: service_healthy

build selects each build context. ports publishes host access. environment changes Order’s URL without changing Java code. Compose creates a default network for these services.

The environment variable is read through ${PRODUCT_SERVICE_BASE_URL:http://localhost:8081} in application-local.yml. Our default Spring profile is local. A later deployment can explicitly activate another profile and supply its configuration.

Running is not ready

Product’s curl check succeeds on HTTP success and fails on a connection error or HTTP error. Spring’s readiness endpoint represents its configured readiness state; it does not prove every business operation or external dependency works.

SettingMeaning
interval: 10sSchedule periodic checks at this interval.
curl --max-time 2Bound the HTTP command to approximately two seconds.
timeout: 3sDocker’s timeout for the whole check.
start_period: 30sGrace period for initial failures; an early success can mark it healthy sooner.
retries: 3Count consecutive failures before declaring unhealthy.
service_healthyGate Order startup on Product passing its health check.

Health checks observe. Dependency conditions gate startup. Neither guarantees future request success.

Product can fail after Order starts. Our client timeouts and ORDR-003 handling still matter. Docker does not restart a container solely because it is unhealthy. Order has no explicit Compose health check yet.

Reference: Docker: startup order.

07 · Restart, recreate, and data

These are different actions. Knowing which one you need prevents many deployment mistakes.

ActionWhat changesWhat does not happen
Build imageProduces an image from current inputs.Existing containers do not switch to it.
Restart containerStops/starts the process in the same container.Does not pick up a new image or changed Compose environment.
Recreate containerCreates a new instance from its configured image/settings.Does not preserve the old instance’s memory or writable layer.
Stop containerStops its processes.Does not by itself delete its writable filesystem layer.
Data locationRestart same containerRemove/recreate container
Java ConcurrentHashMapLost: a new JVM has empty memory.Lost.
Container writable filesystemNormally remains.Lost with the old container.
Named volumeRemains unless explicitly removed.Can be attached again; deleting the volume loses it.
Bind mountHost files remain.Host files remain unless an operation explicitly changes/deletes them.

A volume does not automatically save Java objects from memory. To retain orders, the application must write them to durable storage, such as a database. A database may use a volume for local development, but also needs backup and recovery planning.

Two Order replicas would have separate maps. Restarting one loses its orders; querying another can return 404. Kubernetes will not solve this data-design issue.

Reference: Docker: storage.

08 · Commands by intention

Run Compose commands from the OrderForge root. Read the intention rather than memorizing a long list.

I want to…CommandImportant detail
Start/apply configurationdocker compose up -dCreates/recreates as needed; it is not a source watcher.
Build source and apply imagesdocker compose up -d --buildOur multi-stage Dockerfiles compile Java inside Docker.
See statusdocker compose psRunning is not proof of business readiness.
Follow Order logsdocker compose logs -f --tail=100 order-serviceCtrl+C stops following logs, not the container.
Check runtime userdocker compose exec order-service idExpected UID 10001.
Check Product readinessdocker compose exec product-service curl -fsS http://localhost:8081/actuator/health/readinessRuns inside Product.
Restart current Order instancedocker compose restart order-serviceLoses in-memory orders; does not deploy rebuilt code.
Remove app containers/networkdocker compose downDestroys in-memory orders; named volumes are not removed by default.
Read resolved configurationdocker compose configUseful for errors; output can contain resolved environment values, so inspect before sharing.
See detailed build failuredocker compose --progress plain build order-serviceFind the first meaningful error, not just exit code 1.
Observe resource usedocker statsUse observed memory/CPU to inform limits later.

Do not use broad cleanup commands as a first troubleshooting step. In particular, volume deletion can destroy persistent data. No cleanup command is run by this document.

09 · Troubleshoot in a useful order

Ask: Did it build? Did it start? Is it ready? Can the caller reach it? Is the configuration correct?

SymptomFirst checkLikely explanation
Cannot connect to Docker daemonOpen Docker Desktop; run docker version.The CLI exists but cannot reach the engine.
Maven package exits 1 in DockerUse plain build logs and inspect the first compiler/dependency error.Missing build config, incompatible Java, dependency resolution, or source failure.
Port already allocateddocker compose ps; check existing manual containers/IntelliJ processes.Another process already owns the host port.
Order reports ORDR-003Order logs; check Product status and configured URL.Dependency stopped, wrong port/name, DNS, or timeout.
Product running but unhealthyRead health history and try its readiness endpoint.App still starting, bad path/port, missing curl, or genuine readiness failure.
New code not visibleConfirm image rebuilt and container recreated.Rebuilt JAR alone or restarted old container.
Old order now 404Check whether Order restarted or was recreated.Our data is in memory.
Permission denied after USER changeInspect owner/mode on the exact path.The app is trying to write somewhere it cannot. Grant only the required path, not root privileges.
Works on Mac, not on cloud hostCheck image architecture and platform.ARM64 image versus AMD64 host, or environment differences.
# Inspect actual health-check history for the current Product container:
docker inspect --format '{{json .State.Health}}' "$(docker compose ps -q product-service)"

Product contains curl; Order currently does not. A failed diagnostic command may mean the tool is absent, not that networking is broken. Use a suitable temporary diagnostic container or an available tool when needed.

10 · What a senior Java engineer should know

There is no universal command-count threshold. My suggested bar is: independently build, explain, diagnose, and recover a containerized service, and recognize what the deployment does not guarantee.

PriorityCapabilityWhere we stand
Before KubernetesExplain images, containers, lifecycle, context, ports, DNS, configuration, and memory.Covered and discussed.
Before KubernetesRead a multi-stage Dockerfile and reason about caching.Implemented; review the Lombok failure.
Before KubernetesExplain non-root execution and readiness versus running.Implemented; strengthen through troubleshooting.
Before KubernetesDiagnose a broken service address and recover.Planned hands-on exercise, not yet recorded as completed.
Before productionVersion/publish images; deploy an exact digest and roll back.Not yet implemented. Tags can move; a digest identifies image content.
Before productionManage secrets without baking them into images or committing them.Not yet implemented. Environment variables are configuration, not a secret vault; build secrets need appropriate secret mounts.
Before productionMeasure CPU/memory, configure limits, and leave JVM headroom.Not yet implemented. Heap is only part of process memory.
Before productionHandle SIGTERM, allow in-flight work to finish, and verify shutdown.Exec-form entrypoint helps; graceful behavior and timing still need verification.
Before productionScan dependencies/base images, patch regularly, and control provenance.Not yet implemented. Non-root is one control, not complete isolation.
Before productionUnderstand durable storage, backup, recovery, and replica behavior.Limitations identified; persistence is deferred.
Learn as neededAdvanced networking, custom runtimes, kernel internals, complex BuildKit tuning.Useful specialization; not a prerequisite for our first Kubernetes deployment.

Our production gaps also include automated delivery checks, immutable image references, registry publication, and an agreed recovery strategy. Tests are currently skipped at your request; we will revisit validation when moving toward production readiness.

For JVM memory planning, reserve room for heap, metaspace, thread stacks, direct buffers, and other native allocations. A container memory limit is not the same as the Java heap limit. An OOM kill may prevent the application from logging a useful Java exception.

11 · How to remember

Remember six questions: Build · Run · Connect · Configure · Observe · Persist.

BuildWhat files and Java tools turn source into this image?
RunWhich image, command, user, and resource assumptions start the process?
ConnectWho is calling whom, using which DNS name and port?
ConfigureWhich values change between laptop, Compose, CI, and cloud?
ObserveHow do logs and readiness show what failed?
PersistWhere is the data, and what survives restart or replacement?

12 · Try before revealing

Answer aloud first. Open each card to check your reasoning. These are revision prompts, not a certification score.

Does EXPOSE publish a laptop port?

No. It is metadata. Compose ports or docker run -p publishes a port.

What does 18082:8082 mean?

Laptop/host port 18082 forwards to container port 8082.

Does Order use Product’s published 18081 port?

No. On the Compose network it uses product-service:8081.

Does a rebuilt image update a running container?

No. Recreate the container using the rebuilt image. Restarting the old one is not an image update.

Why did Order need lombok.config copied?

It configures annotation generation for Jackson 3. The build needs configuration as well as source and pom.xml.

Which stage needs source and Maven?

The build stage. The runtime uses the executable JAR and a Java runtime.

Does a health check restart an unhealthy container?

Not by itself. It records health; restart/recovery mechanisms are separate.

Does service_healthy guarantee future order calls succeed?

No. It gates startup. Product can fail later; timeouts and failure handling still matter.

Does a volume preserve ConcurrentHashMap?

No. A volume persists files; the application must write data to durable storage.

Why leave the JAR root-owned?

The runtime user can read it but cannot normally overwrite it or replace it in a root-owned, non-writable app directory.

Is a valid readiness response proof checkout works?

No. It shows the configured readiness check passes, not that every business path succeeds.

What if we run two Order replicas now?

Each has independent in-memory orders. A request hitting another replica may not find the order.

Does --no-cache automatically pull the newest base image?

No. Cache behavior and refreshing the base image are separate; --pull requests a refreshed base reference.

What is the first step after Docker reports exit code 1?

Read earlier detailed build output to identify the actual command and first meaningful error.

13 · Bridge to Kubernetes

We will reuse these application images. Kubernetes manages desired workloads across nodes; it does not compile Java or fix missing persistence.

What you knowNext conceptImportant distinction
ContainerPodA Pod holds one or more containers; initially one application container per Pod.
Start an app instanceDeploymentMaintains desired replicas and supports rolling updates.
Compose service-name discoveryKubernetes Service and DNSStable access to selected Pods, whose addresses change.
Compose health checkStartup, readiness, and liveness probesReadiness controls Service traffic eligibility; liveness/startup failures can trigger restarts.
Environment configurationConfigMap and Secret referencesSeparate deployment values from application images. Secrets still need access control and secure storage configuration.
Published host portPort-forward first; ingress/exposure laterDifferent mechanisms; not a direct one-to-one translation.
In-memory ordersStill in-memory ordersPod replacement loses data. Multiple replicas remain inconsistent.
